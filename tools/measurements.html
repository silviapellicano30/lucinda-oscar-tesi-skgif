Load-time measurements

Measures how long the pages of the SKG-IF version take to load and how often the API calls fail, as perceived by a user of the interface. The API is treated as a black box; every time is also split into waiting for the API and time of the interface, to show how much each part weighs.

Keep this tab in the foreground while measuring (do not switch tabs or minimise Chrome): Chrome slows down hidden tabs. Runs made with the tab hidden or while the browser was offline are flagged (tab_hidden, browser_offline) and excluded from the analysis. Download the CSV at the end of every session: the results are kept only in this browser.

What is measured and why

Method

  • Session = one press of "Start". Each session runs a number of rounds; in every round each selected case is opened once, in a new random order (randomized multiple interleaved trials). Running the trials of one case back to back would expose that case alone to a slow period of the API.
  • Server cache always bypassed (preview=true on every SKG-IF call) and browser cache disabled (no-store): every run measures the real answer time of the API, as for the first visitor of a page.
  • Above the automatic thresholds (250 citations or references in the research product record, 500 publications in the organisation record) the "Load all" buttons are pressed automatically and the time is measured from the click.
  • Every session starts with one warm-up page, not recorded: it opens the connection to the API, so that cost does not fall on the first measured case.
  • A session stops by itself when two runs receive a 429 "too many requests": the agreed load is exceeded.
  • Each run has a time limit; a measure that does not arrive in time is recorded as timeout.
  • Interface time against API time: api_wait_ms is the time in which at least one API call was open (from the request to the end of the reading of its answer); the rest of the measured time belongs to the interface (code, drawing of the page, its own files). long_tasks_ms is the part of the interface time in which the code blocked the page.
  • The pilot session only serves to decide the number of sessions: tick "Pilot session" and its runs are excluded from the analysis (pilot column).

Measures

Values of the measure column; the time is in duration_s. Each measure is also recorded as a W3C User Timing mark with the same name (performance.mark; from the "Load all" click also as a performance.measure), so it can be checked in the Performance panel of Chrome DevTools.

After the sessions

  1. At the end of every session press "Download all runs": every file contains all the runs saved so far in this browser. Always use the same Chrome profile and do not press "Clear results".
  2. Keep all the downloaded files in one folder, with their names unchanged (skgif-timing-runs-....csv): runs that appear in several files are counted once.
  3. Runs to discard by hand (problems of the measuring computer, e.g. it went to sleep): list them in excluded_runs.csv in the same folder, with the columns session_id,round,case_id,measure,reason; an empty round, case_id or measure means all of them. Example: 2026-11-20T09:15:02+01:00,2,,,laptop went to sleep discards round 2 of that session.
  4. From the repository root run Rscript tools/analysis.R <folder>: tables and charts are written in <folder>/analysis. Pilot runs, hidden tabs and offline runs are excluded automatically and counted in excluded_summary.csv.
